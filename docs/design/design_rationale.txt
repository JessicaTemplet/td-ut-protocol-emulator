## Deviations From Original Design

### Deviation 1: Instruction RAM macro — shared dual-port assumption dropped in favor of two single-port memories

**Original assumption (gate budget table above):** "Dual µE Sequencers — Event-driven control units with shared 512×16-bit OpenRAM macro — ~6,000 gates." This treated the instruction store as roughly one line item's worth of area, sized only in gate-count terms, and assumed both engines would draw from one shared 512×16 macro.

**What we found (roadmap item #1, verified against Tiny Tapeout's actual IHP SG13G2 memory catalog at tinytapeout.com/specs/memory):** a 512×16 macro exists, but only as a **dual-port** part, and it costs **3×4 = 12 tiles at 19.5% cell utilization** — half of the entire 6×4 = 24-tile chip budget spent on one RAM, before either engine's control logic, the FIFO, the CRC/NRZI primitives, or the glitch filter exist. The ~6,000-gate estimate was a rough gate-equivalent count that didn't reflect how hard-macro tile packing actually works; the real area cost is roughly double what the budget table implied, and would have made the 18k/24k total impossible to hit once discovered later, after primitives and protocol microcode were already built on top of it (exactly the "find out before building more on top of it" risk the roadmap flagged this item to catch).

**Resolution:** the loader/engine design already never reads and writes instruction memory in the same cycle — writes only happen during the load phase (`run` = 0), reads only during execution (`run` = 1) — so a true dual-port macro was never actually required by the logic, only assumed by the budget table. Tiny Tapeout's single-port catalog includes a **512×8 macro at 1×2 tiles, 41.2% utilization**. Pairing two of these (low byte / high byte) gives a 512×16-equivalent single-port instruction memory for roughly **4 tiles**, versus 12 for the shared dual-port macro.

This also resolves the open "RAM-sharing" decision (former open decision #2): rather than merging µE0 and µE1 onto one shared dual-port macro with two independent read ports, each engine keeps its **own** single-port memory (two 512×8 macros apiece). This is not just cheaper — it's what `engine.ml` and `protocol_engine.ml` already do in RTL (`Ram.create` with one write port + one read port each, as two independent instances) — no RTL change was needed, only the synthesis/hardening target and the documentation of *why* separate single-port memories are the right call rather than a compromise. Estimated total instruction-memory area: ~8 tiles for both engines combined, instead of 12 for one shared dual-port block — cheaper AND simpler to load (no split-address dual-port loader logic needed).

**Action items this deviation drives:** `Loader.addr_width`'s value (9 bits / 512 entries) is unaffected — it was already sized for 512-deep memory regardless of macro shape. The gate/tile budget table above should be read as superseded for the instruction-RAM line item; a real tile count, not a gate-count guess, is now the right unit for that line pending an actual OpenLane pass (roadmap item #3).

### Deviation 2: The target process is IHP CMOS5L, not SG13G2 (found 2026-09-25)

**What happened:** The first months of physical-design work (tile sizes, PDK install, SRAM macro, DRC decks, PDN, the
hardening flow) were done against `ihp-sg13g2`. The competition actually targets a different process, **`ihp-sg13cmos5l`**.
Jane Street's own announcement names "IHP's 130nm CMOS5L process" and points entrants at the "CMOS5L Verilog template".

**Why it was easy to miss:** Tiny Tapeout's regular shuttle (`ttihp26a`, which closed 2026-03-23) uses SG13G2, and both processes
share the same `--ihp` flag in `tt_tool.py`, the same tile sizes, and even the same SRAM macro. What actually selects CMOS5L is the
`PDK` environment variable plus a separate tools branch (`ihp-sg13cmos5l`), a separately pinned PDK checkout (not installed through
`ciel`), and LibreLane 3.1.0.dev3. One template file, the devcontainer Dockerfile, still says `ihp-sg13g2` and is stale. Nothing in the
tooling fails loudly when the two are mixed. It was noticed because a one-line remark in a community chat ("the next tapeout is 5L")
was checked against primary sources instead of being dismissed, and the competition blog post and other entrants' repositories confirmed it.

**What carried over unchanged:** all Hardcaml RTL and all Cyclesim suites (PDK-independent), the SRAM macro (CMOS5L links its SRAM
library to the same files), tile geometry (6x4 = 1289.28 x 710.64 um), and the load-protocol and pin design.

**What had to be redone:** the toolchain install; the DRC and PDN work; the floorplan (see Deviation 4). One finding turned out
to be process-specific and went away: the SG13G2 KLayout deck reports 1,830 violations inside the SRAM macro's own GDS (the open
precheck question), while the CMOS5L deck reports 0 on the same file, so that blocker did not exist for the real target.

**Lesson recorded:** confirm the process name, tools branch and pinned PDK commit from the competition's own CI files
(`tt-gds-action@ihp-cmos5l`) before doing any physical-design work, and keep the regression PDK-independent so RTL work is never
invalidated by a retarget (which is what happened here).

### Deviation 3: Instruction memory was synthesized as flip-flops, about 5x over budget (found 2026-09-16)

**Original assumption:** the instruction store is one line item (~6,000 gates) in the budget table.
**What the first full hardening run showed:** Hardcaml's generic `Ram.create` is mapped by Yosys into individual registers and
multiplexers unless told otherwise: 16,076 sequential cells and **118,642 total cells** for ~24,000 budgeted, with a matching
multi-hour place-and-route. Nothing in the RTL is wrong; it simply never asks for a hard macro.
**Resolution:** `lib/sram.ml` instantiates the vendor macro `RM_IHPSG13_1P_512x8_c3_bm_bist` directly, two per engine (low and
high byte), selected by `create_asic` variants of the engine modules; the plain `create` (behavioral RAM) stays for simulation.
Result: **1,926 standard cells plus 4 macros.** Consequence for verification: Cyclesim only ever sees the behavioral RAM, so a
cocotb bench runs the exact shipped Verilog with the vendor macro model (and later the hardened gate-level netlist) to cover
the macro path (Deviation 6).

### Deviation 4: The SRAM macros needed hand-built power connections and a different floorplan (2026-09-25 to 09-30)

**Problem:** a CMOS5L Tiny Tapeout tile may only route up to Metal4, and its whole power grid is Metal4 stripes. The SRAM
macro's power pins are also Metal4 bars inside its footprint, so there is no layer above from which `pdngen` can drop a via onto
them. Every macro-grid option (PDN-0232 on all variants) and the "same-layer overlap" approach failed; `pdngen` also cuts every
stripe around a macro, leaving the macro pins as islands (17,426 power-grid violations). Global routing was also badly congested
because the old 2x2 stack pointed the macros' signal pins at the die boundary.
**Resolution, in three parts:**
1. Floorplan: all four macros in one row along the bottom, flipped so the power edge faces a small channel and the signal pins
   face the open logic area (`src/config.json`).
2. `src/pdn_macro_bridge.tcl`: after `pdngen`, draws Metal3 straps in the channel, Metal4 stubs under each macro power pin, and
   Via3 arrays at crossings. (A first version shorted VPWR to VGND by covering the other net's via landing pads; LVS caught it, the
   power-grid checker cannot, because it checks each net separately.)
3. `PDN_OBSTRUCTIONS`: Tiny Tapeout's precheck requires every power port rectangle to reach within 10 um of both die edges. Stripes
   cut around the macros started at y=124.9 um (40 violations), so stripes above the macro columns are blocked and only the six
   full-height pairs beside the macros remain; the standard-cell rails above are fed from those. Worst IR drop is 0.074%, so the
   reduced grid is not a power problem.
**Also:** for CMOS5L the precheck runs the KLayout deck (not Magic), so Magic's DRC against the macro uses a trimmed abstract
(`trim_maglef.py`); only the KLayout result on the real GDS gates submission.

### Deviation 5: The as-built architecture differs from the blueprint in several places

- **Instruction word fields.** Blueprint: `[13:10]` pin mask / target. As built: `[13:11]` pin select (1 of 8) and `[10]` a mode
  bit. The mode bit is what lets SHIFT_IO carry CAPTURE, and EMIT_STATE carry a release flag, without new opcodes.
- **Timer range.** Blueprint: payload = raw cycle count, 1023 max. As built: payload counts prescaled ticks and the prescale is
  loaded once. 9600 baud at 50 MHz needs 5,208 cycles, which a 10-bit payload cannot hold.
- **Pins.** Blueprint: a fixed in/out split. As built: the 8 shared pins live on `uio`, each with its own output enable
  (`release_pin`), because I2C needs true open-drain SDA/SCL on one pad and `ui`/`uo` cannot do that. `uo_out` shows the load
  checksum before run, then mirrors the pin outputs.
- **Memory.** Blueprint: "shared 512x16 OpenRAM macro". As built: two single-port 512x8 macros per engine, separate memory per
  engine (Deviations 1 and 3).
- **Configuration interface.** Blueprint: an SPI configuration interface. As built: a byte-serial program loader (prescale
  byte first, then 16-bit words, `engine_sel` picks the engine, a running XOR checksum for verification, `go` latches `run`),
  with no address bus; the same pins double as protocol I/O once running.
- **Backpressure.** Blueprint: Core 0 enters WAIT_DRAIN when the FIFO is full. As built: only the pushing instruction stalls;
  non-pushing instructions never do, which keeps mid-frame bit timing out of backpressure's reach.
- **Phase anchoring.** Built as a prescaled down-counter (timer), as designed.
- **Autobaud edge capture.** Built as CAPTURE mode, which pushes {pin, level, elapsed cycles} into the shared FIFO, giving a
  timestamped logic-analyzer channel using existing FIFO plumbing.
- **Pin ownership.** Per-pin output enables of the two engines are ORed; where both drive a pin, uE1 wins. This is a documented
  assumption, exercised (never contended) by SPI and I2C, not proved.

### Deviation 6: Verification was built differently from the blueprint's plan, and found things the plan would not have

**Plan in the blueprint:** SymbiYosys liveness with `always/eventually`, QuickCheck randomized traces, co-simulation against
Spike/QEMU.
**As built:** directed Cyclesim suites (21), each bug fixed where found (the project log lists about 20 real bugs, e.g. a half-bit
FSM state, a spurious dwell cycle, a false edge when the pin mux switches, a fetch/`pc` alignment bug); a bounded-exhaustive check of
the FIFO over all 4^10 sequences; and an **unbounded SymbiYosys proof** (PDR) of the FIFO. Liveness is encoded as safety ("four
pop-only cycles always leave it empty") rather than `eventually`, which is equivalent for a bounded structure and is what the solver
handles well; covers show the proof is not vacuous. All of these checks were mutation-tested so they can fail. Randomized/QuickCheck
testing and Spike/QEMU co-simulation were not done.
**Findings the original plan would not have produced:**
- The hard-macro path is invisible to Cyclesim; testing the shipped netlist in cocotb closes that gap, including on the hardened
  gate-level netlist.
- Instruction SRAM is not cleared, so a program that runs past its last word executes arbitrary bits (X in simulation). Cyclesim's
  zero-filled RAM hides it. Current rule: end every program with a halt; a hardware guard is optional future work.
- Gate-level simulation with stock Icarus Verilog leaves every vendor flop unknown (their `delayed_*` nets come from `$setuphold`);
  Tiny Tapeout's own iverilog build handles it, and `gl_test/patch_stdcell.py` does for local runs.

### Deviation 7: The differentiating primitives were built last, after the chip itself was submittable (2026-09-30)

The blueprint's novelty claim rests on **hardware NRZI, bit-stuffing and CRC as generic primitives, a glitch filter, and a
demonstration of a USB/CAN-class protocol**. They were deliberately sequenced after the physical flow (Deviations 2 to 4),
because without a chip that clears the toolchain there is nothing to add features to. They are now built:

- **Bit pipe** (`lib/bitpipe.ml`): one `PIPE_BIT` instruction per bit performs NRZI decode, bit un-stuffing, a serial CRC and byte
  assembly. Nothing in it is USB- or CAN-specific: stuffing limit and polarity rule, CRC width / polynomial / reflection / init /
  residue, bytes to skip before the CRC starts, and bit order are configuration, loaded once. USB low speed and CAN are two
  configurations of the same hardware, and UART/SPI/I2C programs simply never use it. Bytes go to the protocol engine through
  the existing FIFO, followed by a status word (CRC ok, stuffing error, byte alignment).
- **Glitch filter** (`lib/glitch_filter.ml`): a pin change is accepted only after N consecutive stable samples (N = 0 is a pure
  bypass with no latency). It sits on the shared pin bus, so both engines see filtered pins.
- **Plumbing**: the new instructions are sub-operations of `SHIFT_IO` with `mode` = 1 (CAPTURE is sub-operation 0, unchanged, so
  every existing program is untouched). Configuration rides the existing loader through a new select bit, `uio[4]`, which costs
  no new pin (pre-run it selects config bytes, post-run it is ordinary pin 4). The protocol engine's word-branch now reaches all
  16 bits of the popped word (payload bit 9), needed to recognise the status word among data bytes.

**What was verified.** The hardware is checked against an independent reference transmitter (CRC, stuffing and NRZI done in the
opposite direction, in plain OCaml): the real USB SETUP token `2D 00 10` (CRC5) and the real GET_DESCRIPTOR data stage with CRC16
`DD 94`, 300 random USB packets with forced stuffing, 300 random CAN frames, and every single-bit line corruption of a packet
rejected. On the dual-engine core, a four-instruction loop receives USB low-speed packets through the real `tt_um_dual` pins
(program and configuration loaded over the pins) and on the shipped Verilog and hardened netlist in cocotb. A 3-cycle glitch on
the sample instant corrupts a packet with the filter off and is absorbed with it on. Five deliberate hardware mutations
(un-stuffing off, CRC feedback dropped, CRC skip ignored, NRZI inverted, filter accepting early) are each caught.

**How fast it keeps up.** The same receive program, re-timed, decodes all test packets down to **8 clock cycles per bit**
(6.25 Mbit/s at 50 MHz) and fails at 7, so the loop has roughly the 5 to 10 cycles per bit budget the blueprint argues a
fetch-and-execute core cannot reach without hardware primitives. USB low speed itself needs 33 cycles per bit at 50 MHz, so the
headroom is about 4x.

**What this does not claim.**
- Receive only. There is no transmit path: `EMIT_STATE` drives a compile-time bit, so hardware stuffing / NRZI / CRC on transmit
  needs the output shift-register opcode noted in `ROADMAP.md`.
- No per-edge resynchronisation. Sampling free-runs from the SYNC edge on a timer, so the test bit period is an exact integer
  number of clocks (32 cycles per bit, i.e. USB low speed at a 48 MHz clock); a real 1.5% tolerant link at 50 MHz would need a
  resync feature.
- Not a USB device: no handshake transmission, no token decoding, no D+/D- level handling.
- The CAN configuration is proven on the bit pipe with generated frames, not yet as a full dual-engine program through the pins.
- The blueprint's second glitch stage, windowed interval validation (rejecting edge-to-edge gaps below a minimum), is not built.
- Manchester / 10 Mbit Ethernet phase tracking is not built.

**Measured numbers that supersede the blueprint's estimates** (hardened, 6x4 tiles, before the bit pipe was added):
1,926 standard cells (28,018 um^2) plus 4 SRAM macros (104,552 um^2); 0.98 mW; setup slack +8.6 ns and hold slack +0.11 ns at the
worst corner; LVS, Magic DRC, route DRC and antenna all clean; precheck passes.

### Deviation 8: A transmit path, and the bit-pipe configuration became a runtime profile table (2026-10-20)

**What changed.** Deviation 7's receive-only bit pipe gained its mirror image, and its single load-once configuration became
a table of profiles that both engines can switch and rewrite while running.

- **Transmit pipe** (`lib/txpipe.ml`): one `EMIT_TX` per line bit shifts the next bit of a byte out, runs the CRC over it,
  inserts stuff bits, and NRZI-encodes, from the same profile layout the receive pipe decodes. After `PIPE_CTRL tx_crc` it
  sends the CRC itself (complemented when the profile says so). A stuff bit takes a step without consuming data, so the program
  still issues exactly one instruction per line bit and never needs to know where stuffing landed. With an all-zero profile it
  is a plain LSB-first shifter (UART), with `msb_first` alone an MSB-first one (SPI).
- **Runtime data**: µE1 decides what is sent. `TX_PUSH` pushes an immediate byte and `TX_ECHO` the byte it last popped into a
  second `Shadow_fifo` instance, each with a `last` flag; µE0's transmit pipe pops it. Reusing the FIFO module means the
  unbounded formal proof and the bounded-exhaustive check cover the TX FIFO unchanged. This closes the "EMIT_STATE drives a
  compile-time bit" limitation (ROADMAP B, "runtime-data output").
- **Profile table** (`lib/profile_table.ml`): four 16-byte profiles (framing, stuffing, CRC up to 32 bits). The receive and the
  transmit pipe each have their own pointer. µE0's `PIPE_CTRL` and µE1's `PROFILE` move them in one instruction; µE1's
  `CFG_WR` writes a profile byte from data it popped.
- **Smaller additions**: `EMIT_TX` open-drain (a 0 drives low, a 1 releases: I2C write data) and differential (the paired pin
  gets the complement in the same cycle: USB D-/D+, RS-485); a `BRANCH_COND` form that tests an internal flag instead of a pin
  (flag 0: the transmit pipe still has data, CRC or a stuff bit to send).

**Why a profile table rather than a wider flat configuration.** The deciding requirement is low-speed USB, a stretch goal of
the challenge: one transaction mixes CRC5 tokens, CRC16 data packets and CRC-less handshakes on one link, so a receiver must
change its CRC between packets based on the PID it just read. A flat configuration loaded once cannot, and the existing tests
had sidestepped it by decoding tokens and data packets in separate runs with separate configurations. With profiles, µE1 reads
the PID and switches the receive pipe (and reloads its CRC from the new profile) between the PID and the first CRC'd bit;
at low speed that window is 33 clocks. A transmit path then needed its own configuration anyway: bridging two protocols
(USB in, UART out) runs two different profiles at the same time. Alternatives considered and rejected:
- One configuration per pipe, rewritten by the program: switching a CRC means rewriting about 12 bytes, far more instructions
  than fit between a PID and its first CRC bit. Kept as an addition instead (`CFG_WR`), for retuning and self-calibration.
- Profiles in SRAM, copied into a working register on switch: denser, but a switch costs about 20 cycles and another macro,
  and area is not the constraint (about 17% of the die is used).
- A fully programmable (microcoded) bit pipe: changes what a profile describes, not how profiles are stored or switched, and
  is far larger. Parity (SWD, PS/2, UART) already works as a 1-bit CRC with polynomial 1.
- Hardware auto-switching (for example after the PID byte): bakes USB into silicon, the fixed-function approach the
  challenge argues against.

**Compatibility.** Profile 0 byte k is configuration index k, and both pointers reset to profile 0, so a host that loads the
original 9 configuration bytes configures exactly what it did before; bytes 9 to 15 extend the CRC to 32 bits (zero means at
most 16, as before). The loader's index only got wider (7 bits). Every existing program, every `tdasm` output and every
gl_test vector is unchanged, and every pre-existing suite passes.

**Deviation from the design note.** The note proposed `TX_LOAD` (µE0 pops a byte into the shift register) next to `EMIT_TX`.
The built pipe auto-loads instead: when a byte is used up, the next `EMIT_TX` takes the next one in the same step. That removes
a bit counter from every program, keeps stuffing invisible to software (a program cannot know where a stuff bit lands, so it
could not know when to load), and frees the encoding.

**A shipped bug the new tests found.** The engine re-arms its timer after every instruction with that instruction's payload
(`load = reg advance`). A timed `WAIT` whose predecessor had payload 1 (`release_pin`, `shift_in_push`, open-drain `EMIT_TX`)
inherited a counter of 0 and expired on its first cycle, ignoring its own payload. The I2C master releases SCL and then waits,
so on the submitted design SCL's high phase was 2 cycles instead of the programmed half period: well-formed in simulation,
and a violation of I2C's minimum SCL high time against a real device. The existing I2C tests passed because their cycle
budget had been sized from the same shortened waits. Fixed in `timer.ml` (`expired` cannot fire on a load cycle); the I2C
tests now check the shortest SCL high phase, which fails on the old timer (2 cycles) and passes on the new one (6).

**What was verified.**
- Transmit pipe alone (`test_txpipe`): bit for bit against independent reference encoders (USB: CRC16 + stuffing + NRZI; CAN:
  CRC15 + both-polarity stuffing), the GET_DESCRIPTOR packet going out as `... 40 00 DD 94`, 300 random USB packets (230 of
  them stuffed, including inside and right after the CRC) and 300 random CAN payloads; and every one looped back through the
  receive pipe to the same bytes with crc_ok.
- On the dual-engine core (`test_dual_tx`): UART frames from µE1's bytes with a constant bit cell across byte boundaries; SPI
  full duplex with a runtime MOSI payload; USB low-speed ACK and DATA0 on differential D-/D+ at 1.5 Mbit/s (33 cycles a bit at
  50 MHz) with a constant cell across the data/CRC boundary and a correct EOP, plus 40 random packets; `CFG_WR` turning a
  profile from LSB- to MSB-first at run time; open-drain output.
- Profiles in use (`test_usb_transaction`): a SETUP token (CRC5) followed by a DATA0 packet (CRC16) in one run, both accepted;
  with switching disabled, either pinned profile accepts only one of the two; 20 random transactions; a corrupted token
  rejected while the following data packet is still accepted; and a USB-to-UART bridge, USB in on profile 0 and UART out on
  profile 1 at the same time.
- Through the real pins and on the shipped Verilog: `test_tt_um_dual_usb_tx` (Cyclesim) and gl_test's `usb_low_speed_transmit`
  (cocotb with the vendor SRAM model) send the GET_DESCRIPTOR packet with the profile loaded over the pins, sampled mid-cell
  against the reference line.
- Mutation check (`run_tx_mutation_test.sh`, part of the regression): 13 injected faults, each caught. Two are worth naming.
  "Wrong CRC polynomial in both directions" survives loopback by construction and is caught only by the reference encoders.
  "TX profile pointer ignored" first SURVIVED: the test bytes 0xA5 and 0x5A are bit palindromes, identical MSB- and LSB-first,
  so the order checks could not fail. They now use 0xA6 and 0x3B.
- `tdasm` assembles a `usb_tx.tds` source to exactly the gl_test vector's words, and places `.profile N` bytes at index 32N+k.

**What this does not claim (yet).** Per-edge clock recovery, link-health reporting and 10 Mbit Ethernet receive (the next items
in the design note) are not built. USB transmit is shown for handshake and data packets; a full device (enumeration, timeouts,
bus turnaround) is not. Not yet re-hardened: area and timing with the table and the transmit pipe are unmeasured.

### Deviation 9: Bit-clock recovery, and why it became a second-order loop (2026-10-24)

**What changed.** A small digital PLL (`lib/clock_recovery.ml`) now tells µE0 when to sample. Its phase counts toward
a bit period from the receive profile (12.8 fixed point, so 33 or 46.67 cycles both work) and raises a strobe at
mid-bit. Each edge on the tracked pin, if it lands within a window of where a boundary is expected, pulls the phase
toward it by (error >> gain shift). `PIPE_BIT` gained a sync form that waits for the strobe, and a `pipe_sync` form
that only waits, so a USB loop can still check for SE0 at the sample instant before stepping the pipe. Profiles grew
to 24 bytes (bytes 16 to 21: enable, pin, gains, period, window); zero means off, so nothing earlier changes meaning.

**Why it is second order.** The design note proposed a proportional correction with a gentle gain. Measured, that is
not enough. Against a sender off by o, a proportional-only loop's phase error settles near 2^gain times the drift
between edges, so with a gain shift of 1, a -2% sender and USB's 7-cell runs the error outgrew the acceptance window,
real edges were rejected and lock was lost. The unit therefore also learns the period: each accepted edge moves a
period estimate by (error >> freq shift), clamped to P +- P/16 and reset on arm. The gains were chosen from a measured
sweep (USB-like data, +-2 cycles of jitter, offsets to +-2%, window P/4): freq shift 4 holds lock at every offset for
phase gain shifts 0 to 3; freq shifts 0 to 2 are unstable, because an edge after a long run carries the whole run's
drift. Beyond about +-2% it is the window, not the loop, that limits lock, and a wider window trades glitch rejection
for range.

**What was verified.**
- Unit (`test_clock_recovery`): one strobe per bit in the middle half of the bit over 2,000+ bits at 33 and at 46.67
  cycles a bit; every phase gain 0 to 3 at +-0.5/1.5/2% with jitter; the proportional-only loss of lock above; the
  learned period within 0.25 cycle of an exact sender and of a 1.5%-fast one; a 3-cycle mid-bit glitch rejected by
  the window (and pulling a sample off-centre when every edge is accepted); overrun when strobes go unconsumed.
- **Against a model.** With snap correction, the last sample before an edge sits at (k + 1/2)(1 - o) of its cell, so
  7-cell runs predict a limit of |o| < 7.0% once detection latency is counted; the measured boundary is +-6.75%. With
  almost every edge rejected (a 1-cycle window) the unit is the free-running sampler it replaces: it passes at 0.3% and
  fails at 1.5% while the tracking unit passes.
- System (`test_usb_rx_recovery`): the USB receive loop with `pipe_sync` and no calibrated waits receives the
  GET_DESCRIPTOR packet at every offset from -2% to +2% with +-2 cycles of jitter, and 15 random stuffing-heavy packets
  at -1.5% and +1.5%. The calibrated timed loop of `test_usb_rx` passes only at 0%: it already fails at +-0.5%, as the
  model predicts for a 96-bit packet (0.52%).
- Through the real pins and on the shipped Verilog: `test_tt_um_dual_usb_rec` (Cyclesim) and cocotb's
  `usb_receive_with_clock_recovery` replay the same committed vector, a 1.5%-fast jittery sender given one symbol per
  clock cycle, good and corrupted.
- Mutation check: five recovery faults (correction sign, window, period-learning sign, strobe position, `PIPE_BIT`
  not waiting) all caught; 18 of 18 in all. One candidate is deliberately not listed: rounding the shifts toward
  minus infinity instead of zero moves the learned period by only 0.02 cycle in closed loop, below what a test can
  separate from jitter.

**A program rule the pin-level benches found.** Armed, the unit takes the next edge as a bit boundary. Armed while the
line was low (SE0 at power-up; the benches' pins read 0 for a few cycles after `go`), the rise to idle J became the
first boundary and idle cells were sampled as data. The Dual-level test never drove the line low first, so it could not
see it. A receive program must wait for the idle level before arming (`br_low 0 idle` ahead of the reset);
`test_usb_rx_recovery` now shows both: the waiting loop receives the packet, the same loop without the wait does not.

**Not claimed.** Link-health reporting (timing margin and CRC syndrome in the status word), Manchester decoding and
10 Mbit Ethernet are the next items. Not re-hardened yet: the recovery and the wider profiles add flops and a 21-bit
datapath whose timing is unmeasured.

### Deviation 10: Link-health reporting (2026-10-24)

**What changed.** The receive path now reports how well it is coping, not only whether a CRC came out right, which
makes the receive side a three-layer error-handling stack: suppression (glitch filter, acceptance window), mitigation
(clock recovery), detection (CRC, stuffing errors, and now margin and syndrome).

- **Timing margin** in the status word's free bits [7:3]: the worst distance between any edge since arm and where the
  clock recovery expected it (accepted or rejected edges alike), as floor(64 x error / P) saturated at 31. Scaling by
  the bit period makes one threshold mean the same for every protocol: bit 7 is "an edge a quarter bit or more off",
  one `br_bit1 7` away for µE1. The division is a 6-cycle sequential divider restarted whenever the worst error grows;
  `PIPE_STATUS` waits for it (it has always finished by then on USB, whose end of packet is two bit cells long).
- **`PIPE_STATUS` word select** (payload[1:0]) instead of a multi-word sequencer: 1 and 2 push the receive CRC
  register's halves (XORed with the residue: the syndrome of a bad packet), 3 the clock recovery's learned period, which
  µE1 can `CFG_WR` back into a profile. One push each, so nothing new to sequence or stall.

**Reported, never corrected.** A receiver that repaired a single-bit error would accept packets a standards-compliant
device rejects, which is wrong for an emulator. The chip hands the host the syndrome; the host decides.

**What was verified (`test_link_health`).**
- The margin is exact: one edge displaced by k cycles after a clean lock reports floor(64|k|/33) for k = 1, 2, 3, 5, 8
  and -2, -5, -8; the worst of several is kept; a clean line reports 0.
- On USB packets the mean margin never falls as the sender's offset grows (0.0, 1.0, 2.0, 2.0, 3.0 at 0 to 2%) or as the
  jitter grows (0.0, 2.0, 5.2, 8.3, 10.5 at 0 to 4 cycles).
- Syndromes: for every one of the 80 single-bit errors in a DATA0 packet's data and CRC, the CRC register µE1 reads,
  XORed with the residue, equals an independent host model of that error's syndrome, and no two positions share one:
  the host can say which bit was wrong. A good packet reads exactly the residue.
- The learned period µE1 reads back for a 1.5%-fast sender: 33.500 cycles (the sender's is 33.495).
- **Warning before failure:** a µE1 program raising a DEGRADED pin from status bit 7, one packet per jitter level: no
  flag at 0, 2 or 4 cycles; flagged with the CRC still good at 6 and 8; CRC failing at 10. The same check runs through
  the real pins in Cyclesim and on the shipped Verilog in cocotb (a committed vector with +-7 cycles of jitter: CRC ok,
  DEGRADED high; the 1.5%-fast, lightly jittered sender: DEGRADED low).
- Mutation check: margin keeping the last edge instead of the worst, a 32 instead of 64 scale, the status word dropping
  the margin, and `crc_lo` reading the high half are each caught; 22 of 22 in all. Not exercised by any test: the
  `PIPE_STATUS` wait for the divider, because every program here issues `PIPE_STATUS` long after the last edge.

### Deviation 11: 10 Mbit Ethernet receive, and what 5 clocks a bit actually tolerates (2026-10-24)

**What changed.** A bit is 100 ns: 5 clocks at 50 MHz, 7 at 70 MHz. No instruction loop keeps up with that, so the
hardware decodes and µE0 runs one instruction per frame (`PIPE_BIT run`), stalled until the frame ends while bytes flow
to µE1.
- **Manchester mode in the clock recovery.** The phase locks to mid-bit edges. An edge within P/4 of where one is due
  is a mid-bit edge and corrects the phase; one further off is a cell boundary and is masked. The bit is the line level
  when the zone closes, a quarter cell after the mid-bit point. Two missing mid-bit edges end the
  frame; bits are handed out one slot late so the sample at the first miss (idle line) is never delivered. Arming snaps
  on a rising edge (a preamble's first falling edge is a cell boundary).
- **Sync-word hunt** in the receive pipe (generic, profile byte 22/23): nothing is delivered until the last 8 bits equal
  the sync word (Ethernet's start-of-frame delimiter, 0xD5), so a receiver that locks partway through the preamble
  still aligns.
- **Octet CRC** (profile byte 23 bit 1): crc_ok is judged at the last whole byte, as IEEE 802.3 has a receiver truncate
  dribble bits; `aligned` still reports them.
- CRC-32 is the existing 32-bit CRC with Ethernet's polynomial, init and residue in the profile. A lost-byte flag
  (BRANCH_COND flag 2) reports bytes the run could not hand over because µE1 left the FIFO full.

**How the decoder got there (each step measured).**
1. A whole-cycle acceptance window lost frames at 0.25 cycle of jitter: with a learned, fractional phase a genuine
   mid-bit edge 1.2 cycles off fell outside a window of 1. Manchester now classifies at P/4, the midpoint between a
   mid-bit edge and a boundary, at full fixed-point resolution.
2. Taking each bit from its edge and ending the frame at the first missing edge ended frames in their preamble: one edge
   pushed past P/4 while the loop was acquiring. Hence the level fallback and the two-miss rule.
3. Where to take the bit: sampling earlier than the zone's close did worse (it can fire before a late but still
   accepted mid-bit edge); taking it from the mid-bit edge's direction measured the same as the level at the zone's
   close, and the mutation check could not tell the two apart, so the simpler level sample is what is built.
4. Period learning, which USB needs, only adds noise here (the standard allows +-0.01%): it is off in the Ethernet
   profile, and the phase gain shift is 2 at 5 clocks a bit and 3 at 7 (from a sweep, `ETH_SWEEP=1`).
5. The remaining frame failures had every byte right and a failed CRC: the line's return to idle, jittered, was now and
   then taken as one more bit. That is exactly 802.3's dribble bit, hence the octet CRC rather than suppressing it.
6. My first bit-error measurement read the decoder's outputs after the clock edge, against stale inputs, and reported
   thousands of errors that did not exist; read at the same point as everything else, the decoder alone is clean.

**What it tolerates (measured, `test_ethernet` and `ETH_BITERR=1`).** At 5 clocks a bit the P/4 budget is 1.25 cycles,
which must cover the edge jitter, a whole cycle of quantization (an edge is seen up to one clock late) and phase noise.
- 50 MHz: 30 of 30 frames at the standard's +-0.01% with up to +-0.5 cycle (10 ns) of edge jitter, and no decoder bit
  errors in 20 streams of ~1000 bits at 0.5 cycle; at 0.6 cycle the decoder slips.
- 70 MHz: 30 of 30 frames with up to +-0.75 cycle (10.7 ns); the decoder alone is clean in steady state up to about
  +-1.0 cycle (14 ns), with its few errors there during acquisition in the preamble, where a flipped preamble bit can fake
  the delimiter (2 of 3 frames at 1.0 cycle).
- Whether that meets 10BASE-T's receive jitter requirement has to be checked against IEEE 802.3 clause 14 before any
  compliance claim; I could not confirm the clause's figure, so none is claimed. What is claimed is the measured table.
- The off-chip front end (transformer, squelch, a comparator to one logic pin) is not part of the chip; the tests drive
  TTL-level Manchester, as a bench FPGA or microcontroller would.

**Verified.** `test_ethernet`: reference CRC-32 checked against the standard check value (0xCBF43926 for "123456789")
and the residue 0xDEBB20E3; 64- to 124-byte frames byte for byte at 5 and 7 clocks a bit; the tolerance table; late
lock with 3 of 7 preamble bytes; a flipped bit and a truncated frame rejected; dribble bits accepted with the octet CRC
and failed without; the lost-byte flag. Through the real pins in Cyclesim (`test_tt_um_dual_eth`) and on the shipped
Verilog in cocotb (`ethernet_receive`), on one committed vector. Mutation check: seven Manchester, hunt, octet-CRC and
run faults added, each caught (29 of 29 in all). Not re-hardened yet; the 70 MHz attempt comes with the harden.
